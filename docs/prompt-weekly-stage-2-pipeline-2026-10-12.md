# Weekly report: этап 2 — довести pipeline на подготовленном входе

Прочитай `docs/weekly-report-stages-2026-10-12.md` и `docs/weekly-stage-1-input-2026-10-11.md`. Проверь hashes и версию артефактов этапа 1. Выполни только этап 2; при отсутствии входного handoff сначала сообщи конкретно, чего не хватает.

1. Прочитай реализацию и ближайшие тесты. Исправь только подтверждённые проблемы из этапа 1: использование сохранённой publication evidence, выбор актуальных Article/observations, precision дат, исключение удалённых rejects, полный weekly scope и совместимый cache reuse. Не помечай все legacy записи достоверными одним флагом.
2. Сохрани разделение обязанностей JEV/Python/DeepSeek, weekly topic taxonomy и quality gates. Daily hold не переносится механически в weekly. Если данных недостаточно для части direction/novelty, существующий отчёт должен сохранять факты и явные статусы; методологию не меняй ради заполнения секций.
3. Подготовь воспроизводимую команду расчёта новой ревизии из private frozen input на изолированной БД с durable journal/cache, лимитом расходов и resume. Не перезаписывай старые pilot manifests. Проверь способ публикации готового результата штатным механизмом без повторного вызова моделей.
4. Выполни содержательные регрессии: подтверждённая исправленная дата учитывается, неизвестная не превращается в известную, stale observation не возвращает reject/старую дату, scope не обрезается, успешный cache переиспользуется, provider failure и ограничения не искажают метрики. Небольшой provider smoke допустим при необходимости, но полный платный прогон относится к этапу 3.
5. Пройди dev-quality-gate с изолированными БД. Зафиксируй изменения в отдельной ветке/коммитах и reviewable PR, исключив чужую архивную работу. Не merge/deploy на этом этапе. При отсутствии необходимых правок зафиксируй проверенный существующий commit и команды; не создавай искусственный diff.

Создай `docs/weekly-stage-2-pipeline-2026-10-11.md`: что исправлено, commit/PR, проверки и ограничения, snapshot/manifest compatibility, точная команда этапа 3, выходные пути, механизм бюджета и reuse, способ публикации готовой ревизии.

Этап завершён, когда pipeline проверен и следующий этап может выполнить расчёт на зафиксированном коде. Production data/report/scheduler сейчас не меняй. Остановись и передай промпт этапа 3.
