# Weekly report: этап 4 — выпустить и опубликовать проверенную ревизию

Прочитай `docs/weekly-report-stages-2026-10-12.md` и handoffs этапов 1–3. Выполни только этап 4. Вход — готовый проверенный payload за 2026-10-11, точный commit и receipts из этапа 3.

1. Проверь hashes, актуальный production image/migration, текущую публикацию за целевую дату и отсутствие более новой конкурирующей ревизии. Убедись, что frozen result соответствует очищенному входу и не возвращает удалённые данные. Изменившееся состояние не подменяй молча старым snapshot.
2. Если нужен новый application code, доведи подготовленный PR через required CI/review, merge и штатный release. Проверяй именно выпускаемый код. Если после этапа 2 были изменения, выполни необходимые проверки и оцени, влияют ли они на готовый payload; зависимый результат нельзя публиковать без повторной валидации. Документальные изменения не требуют новой генерации статей.
3. Сохрани private backup прежнего target report и rollback receipt. Опубликуй проверенный payload новой явной ревизией через существующий publisher/БД, без повторного JEV/DeepSeek-прогона. Менять можно только target report_date=2026-10-11.
4. Проверь публичные API и существующую weekly-страницу: report date/revision, English, темы/секции, метрики, причины insufficient evidence, источники и отображение. Проверь сохранность остальных historical reports и работу daily. Не заменяй это проверкой только локального JSON.
5. Общий weekly cron/автоматическую генерацию пока не включай. Не меняй auth/admission/retention/thresholds. Не запускай новый платный расчёт для демонстрации результата.

Создай `docs/weekly-report-delivery-2026-10-11.md`: URL и revision, commit/PR/release/image, input/payload hashes, итоговые counts/topic states, полный расход этой ревизии, backup/rollback/receipts, проверки API/страницы и честные ограничения выводов. Сохрани завершённые stage reports как историю.

В финале покажи ссылку на опубликованный weekly report и кратко объясни его основные выводы и ограничения. Только этот этап завершает задачу публикации; успешный deploy сам по себе недостаточен.
