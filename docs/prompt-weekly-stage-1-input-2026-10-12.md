# Weekly report: этап 1 — подготовить конкретный вход

Прочитай `docs/weekly-report-stages-2026-10-12.md` и соблюдай общие условия. Выполни только этап 1 для report_date=2026-10-11.

Результат этого этапа — пригодный для следующего шага private snapshot/manifest и точный список проблем интеграции. Не ограничивайся описанием того, что когда-нибудь нужно проверить.

1. Прочитай текущие weekly freeze/classification и publication evidence. Сделай согласованный read-only снимок production для W0/W1/H: Article, относящиеся к ним WeeklyInputObservation, admission/evidence, источники и имеющиеся coverage receipts. Текущий опубликованный weekly за целевую дату зафиксируй отдельно. Сохрани исходный snapshot неизменным, с fingerprint; приватные тексты не выводи в контекст.
2. По сохранённым доказательствам подготовь отдельный manifest отбора. Дай counts по неделям: подтверждённые даты, date-only/неоднозначные, legacy/unknown/conflict; пригодный текст, admission, unresolved. Не считай наличие summary или длину текста доказательством корректности. Не привязывай недатированные записи к неделе по discovered_at; отдельный unassigned pool посчитай с честными ограничениями.
3. Сверь Article с weekly observations: исправленные даты/удалённые rejects не должны быть заменены старыми значениями. Проверь известную проблему: Article без weekly observation автоматически получает legacy_unverified. Зафиксируй точные затронутые группы и желаемый результат для этапа 2.
4. Используй готовые cache/evidence. Содержательные проверки, если нужны для конкретного спорного случая, выполняй ограниченно через JEV/DeepSeek. Дополнительный fetch допускается точечно по сохранённому URL с конкретной целью; не делай общий crawl или массовый повтор. Доказательства новых дат сохраняй в manifest, production Article сейчас не меняй.
5. Проверь coverage W0/W1/H и возможность сопоставимого cohort. Невосстановимые пробелы оставь явными. Найди совместимый старый cache и перечисли основания reuse. Приоритизируй только дефекты, мешающие расчёту выбранного отчёта; нулевой hold во всей БД не требуется.

Создай `docs/weekly-stage-1-input-2026-10-11.md`: counts, исходный snapshot/manifest paths и hashes, точные исключения/неопределённости, конкретные требования к коду этапа 2, границы coverage, стоимость фактически выполненных calls при наличии. Не изменяй application code, production data, scheduler и не запускай полный weekly расчёт.

Этап завершён, когда snapshot и manifest реально существуют, все классы входа учтены, а следующий этап понимает, что исправить и как проверить. Полноту старого сбора выдумывать не нужно. Остановись и дай ссылку на результат и промпт этапа 2.
